Predict before you run.

TraceFirst is a first-year C++ tracer built on one rule: you never run code you have not first predicted. Commit to an answer, then step through the program and watch memory change. When your prediction and the machine disagree, TraceFirst stops at the exact statement where the two parted — and names the idea to fix.

Stage 1
Predict
Read the code. Say what it will print. Lock it in.
Stage 2
Run
Step line by line. Watch each variable's box change.
Stage 3
Investigate
Compare your answer with the machine's. Find the parting line.
Stage 4
Modify
One value changes. Predict again, from your repaired model.
Your field — same code, your world

Every field runs the identical program with the identical numbers. Only the story changes — so a class of mixed majors can argue about one answer together.

    How TraceFirst works: each exercise follows PRIMM — Predict, Run, Investigate, Modify — a sequence from computing-education research. The prediction is not a quiz before the lesson; it is the lesson, because the step-through that follows is read against a model you have already committed to. The four field skins share one code path and one set of numbers, so mixed-major classes discuss the same machine behaviour in four different worlds.
    
      
    

      
    
        
    
          
    Find the bugs. Classify them. Then prove the fix.
    
          
    Three short programs, broken on purpose — from a debugging and code-reading lab built for a first-year introductory C++ course serving CS and non-CS majors together. Click a line to accuse it of being a bug. Every accusation that lands must then be classified, because the distinction this gym trains is the one beginners blur:
    
          
    
            
    Syntax errorThe code breaks a rule of the language. The compiler catches it and the program never runs.
    
            
    Logic errorThe code is legal, compiles clean, and still does the wrong thing. Only the output exposes it.
    
          
    
          
    
            By the end of the gym you can:
            
      
              
    • Read a program you did not write and locate its errors systematically, from a checklist, not by staring.
      • 
              
    • Distinguish syntax from logic errors, with an example of each.
      • 
              
    • Point the stream operators the right way: << out with cout, >> in with cin — and say why main() returns int.
      • 
              
    • Explain operator precedence, the semicolon that detaches an if, and why text needs string and getline.
      •

            Three false alarms — here is the checklist from the lab. Work the program top to bottom and ask, line by line:
            
      
              
    • Semicolons present — after every statement, including using namespace std and return 0?
      • 
              
    • Is main declared correctly — int main()?
      • 
              
    • Stream operators pointing the right way — << for output, >> for input?
      • 
              
    • Types chosen well — string, not char, for text of more than one character, and getline where the answer contains spaces?
      • 
              
    • Formulas right — and is a semicolon sitting directly after an if (condition), detaching its block?

    Where this comes from: the three programs, the bug counts, and the checklist come from a debugging lab module, Find the Bugs — Debugging and Reading Code in C++, built for a first-year introductory C++ course serving CS and non-CS majors together. In the lab you fix the code in an editor; here you train the step before that — seeing the bug, and knowing which kind it is. Scores live only in this session, as in the tracer.
